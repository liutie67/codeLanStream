# gemini 前期调研

> 我想要一个本地或者局域网刷媒体信息流（视频、图片）的工具或者软件，最好电脑、移动端都有，帮我检索github或其他网页是否有相关的项目，或者基于某些组建自己开发？
> 

构建一个局域网内专属的“媒体信息流”（类似于本地的 Instagram、Pinterest 或 TikTok）是一个非常实用的想法。市面上绝大多数开源媒体服务器（如 Plex、Jellyfin）更偏向于“影视库”模式，而不是“无脑刷”的信息流模式。

针对你的需求，我整理了一些现有的开源项目，以及一套非常适合利用你现有技术栈自行开发的架构方案。

### 一、 现有的开源项目推荐

如果你想直接部署现成的项目，可以参考以下几个方向：

**1. 侧重于“时间线信息流”的相册/媒体管理：**

- [**Immich](https://github.com/immich-app/immich):** 这是目前最火的自托管照片和视频备份方案。它的核心 UI 就是一个极高性能的、支持无限滚动的时间线（信息流）。
    - **优势：** 移动端 App（iOS/Android）体验极佳，Web 端也非常流畅。原生支持视频播放，并且内置了基于机器学习的图像/视频内容识别。
    - **契合度：** 如果你的媒体库是以按时间排序的短视频、图片为主，Immich 是开箱即用的首选。
- [**PhotoPrism](https://github.com/photoprism/photoprism):** 同样是基于 AI 驱动的媒体库，支持在 Web 端浏览和过滤媒体流。它的 PWA（渐进式 Web 应用）在手机浏览器上可以像原生 App 一样使用。

**2. 侧重于“标签与发现”的瀑布流（类似 Pinterest / Booru）：**

- [**Szurubooru](https://github.com/rr-/szurubooru):** 一个现代化的、轻量级的自托管 Danbooru 风格图库。
    - **优势：** 适合重度依赖标签管理的媒体。UI 是经典的瀑布流，支持视频（WebM/MP4）和图片。
    - **契合度：** 只有 Web 端，但移动端适配不错。
- [**Hydrus Network](https://github.com/hydrusnetwork/hydrus):** 虽然它的客户端是纯 PC 端的，但它强大的本地媒体管理能力无可匹敌。社区提供了很多第三方 Web 前端（如 `hydrus-web`），可以通过 API 在局域网手机上刷本地图包和视频。

### 二、 基于现有组件自行开发（推荐方案）

考虑到你拥有强大的本地算力（如 RTX 4090），并且在 Python 环境管理、Web 抓取以及大模型（Ollama/Whisper）本地推理方面有丰富的实战经验，**自行开发一个轻量级信息流 Web App 可能是最灵活的选择**。你可以轻松将平时抓取的视频流、AI 生成的总结无缝接入进去。

### 推荐技术栈与架构

- **后端 (Backend): FastAPI (Python)**
    - **原因：** 轻量、异步并发性能极高，且能完美契合你现有的 Python 数据处理脚本。你可以使用 `uv` 来极速构建和管理这个项目的依赖。
    - **核心逻辑：** 扫描本地媒体文件夹，提取元数据（时长、分辨率），并将路径和元数据存入 **SQLite**。通过 FastAPI 提供分页 API，将媒体流切片传输给前端。
    - **进阶玩法：** 可以直接与 `yt-dlp` 的下载目录打通。利用后台任务跑 `mlx-whisper` 提取字幕，再调用本地大模型生成视频摘要。在刷信息流时，视频下方直接显示 AI 总结。
- **前端 (Frontend): Vue 3 + TailwindCSS (构建 PWA)**
    - **原因：** 构建响应式 Web 页面。使用 PWA (Progressive Web App) 技术，手机浏览器访问局域网地址后，可以直接“添加到主屏幕”，体验与原生 App 几乎一致，免去分别开发安卓/iOS的麻烦。
    - **核心组件：**
        - *瀑布流组件*：例如 `vue-masonry` 用于图片流。
        - *无限滚动 (Infinite Scroll)*：利用 `Intersection Observer API`，当用户刷到页面底部时，自动向 FastAPI 请求下一页的数据。
        - *视频播放器*：使用 `Video.js` 或 HTML5 原生 `<video>` 标签，配合滑动监听，实现“滑到哪个视频，哪个视频自动播放”的类似短视频平台的交互。
- **桌面端扩展 (可选): Tauri 或 Electron**
    - 如果你希望 PC 端有一个独立的软件，可以直接将上述写好的前端页面用 Electron 打包，或者用基于 Rust 的 Tauri 打包（更轻量）。

### 最小可行性产品 (MVP) 开发步骤：

1. 写一个 Python 脚本，遍历目标媒体文件夹，生成包含 `[id, file_path, type(video/image), date_added]` 的 SQLite 数据库。
2. 用 FastAPI 写两个接口：`/api/feed?page=1` (返回分页的媒体列表) 和 `/media/{id}` (返回文件流媒体流)。
3. 写一个单文件 HTML（引入 Vue CDN），实现无限下拉和基础的图片渲染/视频播放。

基于你期望的功能，我强烈建议**自己基于现代开源组件搭建一套系统**。这不仅能完美契合你的需求，还可以与你现有的本地 AI 算力、视频抓取脚本等无缝集成。

以下是我为你设计的全栈实现方案和核心技术建议：

### 一、 核心技术栈推荐

- **后端驱动:** `FastAPI` (Python) + `SQLAlchemy`。非常适合处理媒体流和构建高并发 API，你可以继续使用 `uv` 来管理依赖，保持极致的开发速度。
- **数据库:** 对于“庞大”的媒体库，建议直接上 `PostgreSQL`，其对复杂查询（筛选、随机、标签）的支持远超 SQLite。
- **前端框架:** `Vue 3` + `TailwindCSS`。打包为 PWA 解决移动端访问，或者套一层 `Electron` 解决 PC 端原生体验。
- **媒体处理核心:** `FFmpeg` (自动化脚本调用)。这是生成封面和预览图的灵魂。
- **前端播放器组件:** **`ArtPlayer.js`**。这是实现你需求的关键组件，它原生支持 B 站风格的悬停预览、极速加载，并且高度可定制。

---

### 二、 核心功能实现方案建议

### 1. 媒体库抓取与分类过滤

- **自动抓取:** 后端启动一个后台任务（可以使用 Python 的 `watchdog` 库），实时监控你的目标目录。新文件存入数据库时，记录其绝对路径、相对文件夹结构、扩展名和创建时间。
- **筛选机制:** 数据库设计时，将“文件相对路径”作为一个字段。前端请求时，通过 API 传递参数（如 `?type=video&folder=/downloads/yt-dlp/&sort=time_desc`），后端直接拼装 SQL 返回结果。

### 2. “小红书式”多列瀑布流与自动封面

- **排版实现:** 在 Vue 中使用瀑布流组件（如 `vue-masonry` 或纯 CSS 的 `column-count`）。
- **封面生成 (难点):** 不能让前端去截取庞大视频的封面，会卡死浏览器。
    - **建议:** 后端在扫描到新视频时，自动调用 FFmpeg 截取第 1 秒或关键帧作为封面，并生成一张 WebP 格式的图片存储。
    - `ffmpeg -ss 00:00:01 -i input.mp4 -frames:v 1 -q:v 2 cover.webp`
    - 瀑布流直接加载这些轻量的 WebP 图片。

### 3. “TikTok式”单屏上滑自动播放

- **交互逻辑:** 前端使用 `Swiper.js` （Vertical 模式）或通过 `Intersection Observer API` 监听 DOM 元素。
- **性能优化 (极其重要):** 浏览器同时挂载几十个 `<video>` 标签会崩溃。你必须实现“视频实例销毁机制”：只保留当前屏幕、上一屏和下一屏（共3个）的视频处于 `<video>` 状态，其他的全部替换为封面图片。滑到对应位置时再动态初始化播放器并 `play()`。

### 4. PC 端鼠标悬停进度条快速预览

- 这个功能专业术语叫 **"Sprite Thumbnail" (雪碧图预览)**。
- **后端处理:** 使用 FFmpeg 将视频每隔几秒截取一张小图，然后拼接成一张大图（雪碧图），并生成一个 `.vtt` 格式的字幕文件，记录时间轴对应的大图坐标。
- **前端集成:** 将生成的雪碧图和 VTT 文件喂给前端的 `ArtPlayer.js` 或 `Video.js`，它们内置了原生支持，鼠标放上去就会自动切图预览，无需额外开发复杂的逻辑。

### 5. 回收站、收藏夹、标签与“随机刷 10 个”

- **回收站:** 数据库里加一个布尔字段 `is_deleted`。点击删除只是将其设为 True（软删除），前端不再展示。保留一个物理删除的 API 供以后清理空间。
- **标签与收藏:** 标准的多对多（Many-to-Many）数据库关系。
- **随机刷 10 个:**
    - 传统写法：`SELECT * FROM media ORDER BY RANDOM() LIMIT 10;` （数据量小没问题）。
    - 大数据量优化：如果是百万级媒体库，建议后端在内存中维护一个 ID 列表，每次从中随机取 10 个 ID，再去数据库查详情，速度极快。

### 三、 进阶融合玩法（发挥算力优势）

既然这套系统是自己开发的，你完全可以将其与你现有的 AI 工作流结合：

1. **AI 自动打标签:** 在后台抓取媒体后，顺便调用本地的视觉模型（如 CLIP 模型或 YOLO）识别视频/图片内容，自动写入数据库标签（如：“汽车”、“风景”、“游戏”），彻底解放双手。
2. **内容摘要联动:** 如果是带有解说的视频，后台提取音频并用 Whisper 转写，再由大模型生成一句话摘要，直接显示在 TikTok 视图的视频标题处。

**开发起步建议：**

不要一开始就追求全功能。先写一个最小可行性脚本：**用 FastAPI 扫描一个测试文件夹，提取路径存入数据库，然后写一个简单的 HTML 页面用瀑布流展示出这些视频的封面**。走通这第一步，后面的弹窗播放、滑动逻辑和雪碧图都可以像搭积木一样逐步添加。

> 关于卡顿，在ssd电脑本地应该没问题，如果部署到nas，机械硬盘和全闪硬盘或者macos的文件共享smb协议等能支持很快的刷视频预览，不好看就滑走的操作吗？
> 

这是一个非常直击痛点的问题！当从“本地单机”切换到“局域网 NAS”时，“存储介质的物理特性”**和**“网络传输协议”将直接决定你能否获得丝滑的“TikTok式”刷视频体验。

直接给出结论：**如果架构不经优化，使用机械硬盘 NAS 和原始 SMB 协议，快速滑动的体验一定会灾难性地卡顿。但通过合理的架构设计，完全可以实现丝滑秒播。**

下面为你详细剖析这其中的技术瓶颈以及解决思路：

### 一、 硬件层面的瓶颈分析

快速“刷”视频（不好看就滑走）在底层引发的操作是**高频的随机读取（Random Read）**。

- **机械硬盘 (HDD NAS):** * **致命弱点：** 机械硬盘的强项是大文件的连续读取，但它的寻道时间极长（通常在 10ms-20ms 之间）。当你快速滑过 5 个视频时，磁头需要疯狂地在盘片上跳跃来寻找不同的视频文件头部数据。
    - **体验：** IOPS（每秒读写次数）瞬间被打满，硬盘狂转，前端画面会一直转圈缓冲，无法实现“滑到即播”。
- **全闪 NAS (All-Flash SSD):** * **优势：** 寻道时间几乎为 0，随机读取性能是机械硬盘的成百上千倍。
    - **体验：** 磁盘性能不再是瓶颈，体验非常接近本地 SSD。此时的瓶颈转移到了你的局域网带宽（千兆/2.5G/万兆 LAN 或 Wi-Fi 6/7 的握手速率）。

### 二、 协议层面的误区与正确姿势

你提到了 macOS 的 SMB 协议，这里需要**纠正一个架构上的误区**：现代的 Web App 或移动端 App，**绝不能直接通过 SMB 协议去串流视频流给前端**。

- **SMB 的劣势：** 它是文件共享协议，握手和权限验证的 Overhead（额外开销）非常高。它不支持前端播放器（如 Video.js）进行灵活的字节级跳跃播放。
- **正确的流媒体协议 (HTTP Range Requests)：**
    
    你之前构思的 FastAPI（或配合 Nginx）在这里就派上大用场了。
    
    1. 你的**后端服务器**（比如部署在 Mac 或软路由上）通过 SMB 协议将 NAS 的媒体文件夹挂载为本地目录。
    2. 后端 FastAPI 读取这些文件，并通过 **HTTP 206 Partial Content (分段请求)** 协议暴露给前端。
    3. 这样，前端播放器只需要请求视频前几兆的头部数据（moov atom）就能瞬间起播，无需等待整个文件传输。

### 三、 实现“丝滑秒播”的核心软件优化方案

如果你不想花大价钱买全闪 NAS，只要在软件和架构上做好以下三步，**即便视频存放在机械硬盘 NAS 里，依然可以做到丝滑体验**：

### 1. 动静分离：让 SSD 承担所有随机 IO

机械硬盘只适合安静地提供持续的大流。

- **做法：** 你的数据库文件（PostgreSQL/SQLite）、所有视频的**封面图片 (WebP)**、**悬停预览雪碧图 (Sprite)** 都必须强制存放在**本地电脑的 SSD** 或 NAS 的 **NVMe 固态缓存盘**上。
- **效果：** 用户在疯狂滑动时，前端加载的全是 SSD 上几十 KB 的图片和数据库记录，丝般顺滑。只有当用户停下手指，决定播放当前视频时，才向机械硬盘发起真实的视频数据请求。

### 2. 前端预加载策略 (Preloading)

这是短视频 App 不卡顿的终极秘密。

- **做法：** 假设屏幕正在播放第 `N` 个视频。前端代码在后台默默地发起请求，通过 HTTP Range 提前拉取第 `N+1` 和 `N+2` 个视频的前 `1MB` 数据（包含视频元数据和关键帧）存入浏览器内存。
- **效果：** 当用户滑到下一个视频时，播放器从内存中瞬间读取头部数据直接起播，完美掩盖了 NAS 网络传输和机械硬盘寻道的延迟。

### 3. 异步生成“代理流” (Proxy Media) —— 推荐玩法

如果你 NAS 里存的都是几十 GB 的 4K 原盘或者高码率素材，即便是全闪 NAS 配合 Wi-Fi 6，瞬间并发加载也会卡顿。

- **做法：** 既然你的工作站拥有顶级的算力，你可以编写一个 Python 后台守护进程。当发现 NAS 有新视频加入时，利用强大的 GPU 算力，在后台静默调用 FFmpeg (NVENC) 将视频压缩出一份 **720p/1080p、H.264 编码、非常利于网络串流的“代理版本 (Proxy)”**。
- **效果：** 用户在“信息流”视图疯狂滑动时，后端只推送轻量级的代理视频，加载极其迅速。如果用户觉得这个视频有价值，点击进入详情页或全屏时，再提供一个“切换原画”的按钮去读取几十 GB 的原文件。

**总结来说：**

不要依赖前端直接读 SMB。利用 FastAPI 做中转提供 HTTP 流，利用固态硬盘存储封面和数据库，配合前端的视频头部预加载，就能在普通的机械 NAS 上实现极佳的流媒体体验。
